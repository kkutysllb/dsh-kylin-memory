# 0201 缺陷分析与业界对标（v0.1.0）

> 状态：2026-10-02 基于 v0.1.0（commit 0d07a6c）的代码静态分析与业界对标。缺陷编号（A1..D4、B1..B5）是稳定引用 ID，实施计划（docs/03-plan/0302）与路线图（0301）均按 ID 引用；修复落地后请在本文对应条目标注 ✅ 与版本号，不允许陈旧。

## 背景与方法

对 v0.1.0 全量源码做静态走查，结合四类业界成功案例的公开资料做能力对标：Zep/Graphiti（时序知识图谱）、Mem0（整合管线）、Letta/MemGPT（agent 自编辑分层记忆）、HippoRAG 2（PPR 多跳检索）。方法边界：无生产流量数据，结论来自代码与文档推演；触发条件列标注每个缺陷在什么使用强度下开始真实伤害。

## 总评

工程纪律优秀（合同校验、隔离、幂等、fail-open、双宿主零分支）、检索管线完整（双路 RRF、本地 LPA/PPR），但记忆**生命周期管理缺位**：只增不减、无事实失效、无整合、无作用域。个人 profile 小规模下一切正常；以下 A 类缺陷随使用时间**必然**触发。

## A. 正确性与一致性（P0，随时间必然恶化）

### A1 无事实失效机制 —— 与业界差距最大 ✅ v0.1.1（轻量版：triple 级 superseded_by，轻于双时间轴，谓词字面匹配为 v1 边界）

同一事实先后矛盾（"端口改为 9090" → "改回 8080"）时两条记忆都活着且同等可召回，仅靠 `updated_at` 排序软兜底。上游 20 轮基准的场景设定恰恰是"刻意修改已确立的事实"，说明这是核心场景而非边角。

- 触发条件：任意一次事实修订（使用数天后必现）。
- 业界参照：[Zep/Graphiti 双时间轴](https://arxiv.org/abs/2501.13956)——每条边 `(t_valid, t_invalid)` + `(t_created, t_expired)`，新事实到达时旧边**标记失效而非删除**，支持任意时点查询。Mem0 用 UPDATE/DELETE 决策从记忆层解决。
- 现成基础：旧概念图 schema 里 `SUPERSEDES` 边类型与 `temporal` 字段已存在，轮次记忆层完全没用上。
- 关联代码：`src/store/store.ts`（upsertTurnMemory/replaceNavigationTriples）、`src/recaller/recall.ts`。

### A2 实体归一化只有空白规范化

"发布端口"/"端口"/"deploy port" 是三个独立导航词项；term 种子匹配靠字面双向子串，同义词/别名/中英混写全部失配，图路线召回率被实体碎片化卡死，多跳检索名存实亡。

- 触发条件：实体以不同表述反复出现（常态）。
- 业界参照：Graphiti 做 LLM 辅助实体消解 + 模糊合并；[HippoRAG 2](https://arxiv.org/abs/2502.14802) 做短语归一化且把 passage 节点放进图参与 PPR。
- 关联代码：`src/store/store.ts` upsertNavigationTerm（仅 `trim` + 空白折叠）。

### A3 无记忆整合（consolidation），纯追加（部分缓解：B5 新鲜度衰减 ✅ v0.1.1；LLM 整合仍推迟）

同一话题 20 轮 = 20 条独立摘要；重复 SPO 权重滚雪球（有意设计），但与 B5（无时间衰减）叠加后老话题长期垄断 PPR。Mem0 的两阶段管线在抽取后由 LLM 决策 ADD/UPDATE/DELETE/NOOP（[arXiv 2504.19413](https://arxiv.org/html/2504.19413v1)）；我们零整合。

### A4 抽取提示词中文写死，跨语言行为未定义

`src/extractor/extract.ts` 的 system prompt 与 few-shot 全中文。英文会话的摘要/三元组语言跟随会话还是提示词，未定义、未测试；摘要语言与查询语言不一致时向量相似度下降、词项直接失配。

### A5 Embedding 降级后永不恢复

启动 ping 失败 → `embeddingState="degraded"` → 词法召回直到进程重启。无周期性重探针、无显式告警。触发条件：一次网络抖动。

## B. 检索质量（P1）

| ID | 缺陷 | 细节 | 参照 |
|---|---|---|---|
| B1 | 词法回退是全短语 LIKE | 无分词（中文"端口 9090"查不到"9090 端口"）、大小写/语序敏感；轮次记忆层没有 FTS5（FTS5 只在旧图节点上） | Zep 用 Okapi BM25 |
| B2 | 图路线种子依赖字面命中 | 查询不含记忆原词则图路线整条失效 | HippoRAG 2 phrase+passage 双种子 |
| B3 | 无 reranker / MMR / 多主题查询拆分 | Top-K=6 直接进上下文；多主题单问漏召回（README 已承认） | Zep/Mem0 接 cross-encoder |
| B4 | 相似度阈值 0.70 单模型单语料校准 | 换 embedding 模型/语种即失效；有 env 覆盖无自适应 | 成功案例用相对分位或校准集定标 |
| B5 | ~~重复 SPO 权重无时间衰减~~ ✅ v0.1.1（freshnessHalfLifeDays 默认关） | PPR 中老记忆压制新记忆 | Zep 从图结构（失效）解决 |

## C. 架构与工程（P1/P2）

- **C1** 新旧双数据模型共存：`km_record` 概念图与轮次导航图并存，旧图 PPR/社区 API 生产路径无调用方，两套索引白付维护成本。
- **C2** 向量暴力全表余弦（无 ANN）+ 召回路径 N+1（getTurnMemoriesByIds / toTurnMemory / triples 回查）。万级记忆后成热点。
- **C3** ~~无 CI~~ ✅ v0.1.1（GitHub Actions）。
- **C3 历史** 无 CI：上游 `.github/workflows` 未移植；质量门只在本地 `pnpm check`。
- **C4** ~~`test/helpers.ts` 手工复刻 schema~~ ✅ v0.1.1（改用真实 migrate()；漂移曾在 m17 当场兑现为 bug）。
- **C5** 记忆无修订历史与删除审计：`km_forget` 即永久消失，无回收站/journal（Mem0 有 history db；旧图反而有 node_revisions）。
- **C6** 基准未移植：上游 `benchmarks/`（20 轮场景 + JSONL 账本 + 复算脚本）不在本仓库，"省了多少上下文"没有自己的可复现证据。教训：[Mem0 自报基准并删除不利结果引发反噬](https://x.com/S_BatMan/article/2075727897948536843)——基准必须可复跑、结果全保留。
- **C7** `extraction_next_retry_at` 列从未启用（上游有意不自动重试，张力已记录于 0301）。
- **C8** 启动时全量 `syncEmbed` 旧节点，大库拖慢启动。

## D. 边界、安全与隐私

- **D1 ~~无作用域/多租户（第二危险）~~ ✅ v0.1.1（workspace_id + recallScope，逻辑隔离；硬多租户仍不做）：跨项目/跨会话召回是特性也是风险——公司项目记忆流入个人会话、A 客户记忆流入 B 客户。全局单 SQLite 池，连 allowlist 配置都没有。Mem0 一级参数即 `user_id/agent_id/run_id`。个人单机是特性，多人/多项目是事故。
- **D2 召回注入的提示词注入面**：召回快照是历史对话原文，仅靠文本声明"不可信历史参考"；旧会话若被诱导写下"忽略后续指令"，会经摘要/SPO 固化并在未来会话回注。
- **D3 备份与导出缺失**：记忆资产单文件，无 export/import/dump；VACUUM 手动。
- **D4 小脏点**：`sessionKey` 前缀硬编码 `"dsh:"`（Kylin 宿主落库数据语义混乱）；`km_signals` 废弃表仍在建。

## 对标矩阵

| 能力 | 本插件 v0.1.0 | [Zep/Graphiti](https://github.com/getzep/graphiti) | [Mem0](https://docs.mem0.ai/core-concepts/memory-evaluation) | [Letta](https://www.letta.com/blog/agent-memory) | [HippoRAG 2](https://arxiv.org/abs/2502.14802) |
|---|---|---|---|---|---|
| 事实失效/时间 | ❌ 排序软兜底 | ✅ 双时间轴+边失效 | ⚠️ UPDATE/DELETE 决策 | ⚠️ 核心记忆自编辑覆盖 | ❌ |
| 实体消解 | ❌ 空白规范化 | ✅ LLM 辅助+模糊合并 | ⚠️ 靠 consolidation | — | ✅ 短语归一化 |
| 记忆整合 | ❌ 纯追加 | ✅ 图演化 | ✅ ADD/UPDATE/DELETE/NOOP | ✅ agent 自编辑 | — |
| 检索 | 向量+LIKE+PPR+RRF | BM25+余弦+图+reranker | 向量(ANN)+图 | 向量+全文 | PPR 多跳 |
| 记忆编辑者 | 系统管线（被动） | 系统管线 | 系统管线 | **agent 主动** | 系统 |
| 作用域 | ❌ 全局单池 | ✅ 按图分组 | ✅ user/agent/run id | ✅ 按 agent | — |
| 通用基准 | ❌（仅上游自建场景） | ✅ DMR 等 | ✅ LoCoMo 92.5 / LongMemEval 94.4（自报有争议） | ✅ | ✅ 公开 |
| 每轮成本 | **1 次抽取调用（最省）** | 多次 LLM（重） | 2 阶段 LLM | 视 agent 行为 | 离线索引+1 次 |

我们反而占优的两点：**每轮恰好 1 次辅助调用的成本模型**；**失败语义与防御性工程**。定位结论：补齐方向是"生命周期管理"，不是堆 LLM 调用。

生态内洞察：Letta 的 agent 自编辑哲学所需的基础设施我们已有（`km_search/km_record/km_forget` 就是记忆编辑工具），但 `assistantTools` 默认 `none` 把模型完全排除在记忆管理之外。在长会话宿主里默认放开 `search` 是零架构成本的哲学升级（列入 0302 可选项）。
